# 6. EF Core through value converters (column-bound), Dapper through explicit parameters (row-bound)

- Status: accepted
- Date: 2026-11-13

## Context

Applications use EF Core and Dapper. Ideally every ciphertext is bound to its row (ADR 0002), so a value copied from
patient A's row to patient B's row fails to decrypt.

## Options considered

1. **EF Core value converters.** Transparent for the application: properties stay `string`, queries and change tracking
   work. Converters are synchronous and see one value with no entity, so no row key; and they run for query parameters
   too (an equality filter encrypts the constant with a fresh nonce and matches nothing).
2. **EF Core SaveChanges and materialization interceptors** that encrypt into shadow properties with the primary key in
   the context. Row binding, but keys generated by the database are unknown before insert, and the application would
   work with two properties per field.
3. **Dapper: explicit parameters** (`AddEncrypted(name, value, encryptor, context)`) with the row key known at the call
   site, and explicit decryption on read.

## Decision

Option 1 for EF Core and option 3 for Dapper, with the difference documented and tested instead of hidden.

- `IsEncrypted(encryptor)` fixes the context to the mapped table and column at model-building time.
  `HasBlindIndex(source, index, definition)` plus `BlindIndexInterceptor` keeps index columns in step with their source on
  every insert and update. `WhereBlindIndexMatchesAsync` filters by the index in SQL and drops false positives after
  materialisation.
- The key ring offers a genuinely synchronous path for converters (the "bool async" pattern; HttpClient.Send in the OCI
  adapter), so no sync-over-async blocking happens on a cache miss.
- Because converters capture the encryptor, the demo's context uses a model cache key per encryptor.

## Consequences

- An integration test and the demo show both behaviours: a national id copied into another column fails in EF Core; a
  national id copied into another row of the same column decrypts (EF Core, column-bound), while a lab note copied to
  another row fails (Dapper, row-bound).
- Equality filters on encrypted EF properties silently match nothing; the docs and a test say to use the blind index.
- A table written by both EF Core and Dapper must agree on binding per column; the re-encryption job takes the binding
  per column (`EncryptedColumn(name, rowBound)`).
- Building a new EF model per key ring costs hundreds of milliseconds (measured in the first-read benchmark); production
  has one key ring per process, so it is paid once.
